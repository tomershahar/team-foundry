# Spec 04: Lightweight Drift Automation

**Status:** Conditional; manual Status and PR CI gate already delivered  
**Outcome:** Teams are reminded about likely context drift without installing a server or blocking routine work.  
**Start gate:** Evidence from Doctor usage or user interviews shows ongoing decay after initial setup

## Problem

`status`, `status --ci`, and `init-ci` already detect missing files, broken links, staleness,
and some unlinked product context. The remaining question is whether users need automatic,
change-aware reminders. This spec tests that with repository-native automation.

Local git hooks are not the first implementation: they are not cloned by Git, vary by
environment, and create another installation lifecycle. The first slice extends the
existing GitHub workflow because it is visible, reviewable, and already generated by the CLI.

## Proposed Behavior

Extend the generated workflow with:

- Existing pull-request drift gate unchanged.
- `workflow_dispatch` for explicit runs.
- A weekly schedule for context health review.
- A change-aware warning when substantial product/code changes occur without any tracked
  context file changing in the comparison range.

The first release warns and exits zero for the change-aware heuristic. Missing files and
broken links retain current CI failure behavior. A feature commit does not always require
a context update; the tool must say "review suggested," not "documentation is wrong."

## Detection Contract

Implement a pure comparison function over changed paths:

```text
codeOrProductChanged = changed path matches configured source/product patterns
contextChanged       = changed path is AGENTS.md, a pointer, team-foundry/**,
                       or .team-foundry/**
reviewSuggested      = codeOrProductChanged && !contextChanged
```

Default product/code patterns should be broad and explainable, with generated workflow
configuration allowing teams to add paths. Commit-message classification is not part of
the first slice; it is too noisy to be an enforcement oracle.

## Architecture

- `src/drift.ts`: pure changed-path classification and concise result rendering.
- `src/index.ts`: a machine-oriented command used by the workflow, exact name chosen during planning.
- `src/templates/ci-workflow.ts`: PR, manual, and scheduled triggers.
- `src/__tests__/drift.test.ts`: path and exit behavior.
- `src/__tests__/ci.test.ts`: generated workflow assertions.
- `docs/ci.md`: warning semantics, configuration, and limitations.

The command may reuse status analysis but must not parse human-formatted Status output.

## Non-Goals

- No MCP server, daemon, background process, telemetry, or mandatory local hook.
- No semantic commit-message classifier or LLM call.
- No automatic edits to context files.
- No strict failure for "code changed, context did not" in the first release.
- No overwrite of an existing customized GitHub workflow.

## Development Track

### 1. Product and Technical Planner

- Review Doctor feedback and identify the user evidence that satisfies the start gate.
- Specify the exact changed-path source available for pull requests, schedules, and manual runs.
- Define shallow-clone behavior and comparison fallbacks.
- Show the generated workflow diff and stop for approval.

### 2. Test Author: Red

Add failing tests for:

- Source changes without context changes produce `reviewSuggested: true`, exit zero.
- Source plus context changes produce no suggestion.
- Docs-only, dependency-lock, and generated-output changes do not trigger by default.
- Missing/broken context preserves existing CI failure behavior.
- Manual and scheduled workflow triggers are generated.
- Existing workflow is never overwritten.
- Empty or unavailable comparison range degrades to a normal Status run with an explanation.
- Paths containing spaces and Windows separators are normalized safely.

### 3. Developer: Green

- Implement pure path classification before workflow wiring.
- Keep warning language factual and non-accusatory.
- Add configuration only where a real fixture needs it.
- Preserve current PR gate behavior and output.

### 4. Test Verifier

Run focused drift and CI tests, typecheck, lint, and build. The user runs `npm test`.
Validate the generated YAML with a structured parser rather than string matching alone.

### 5. Independent Code and Security Review

Review for:

- Shell injection through changed filenames or revision arguments.
- Incorrect comparison ranges on pull requests and schedules.
- Warning logic accidentally becoming a hard failure.
- Workflow permission expansion or unpinned third-party actions.
- Destructive replacement of customized workflows.
- Noisy defaults that would teach users to ignore the signal.

### 6. UAT / Noise Trial

Run the workflow for at least two weeks in this repository or a controlled fixture. Label
every warning useful, false positive, or unclear. Pass when at least 80% of warnings are
judged useful and no normal PR is blocked by the heuristic.

## Acceptance Criteria

- Automation remains local/GitHub-native and requires no service.
- Existing hard-fail semantics are unchanged.
- Change-aware reminders are warning-only, explainable, and low-noise.
- Generated workflows are safe, valid, and never overwrite customization.
- The two-week noise trial passes before broader promotion.

## Stop Conditions

Do not implement this item if Doctor research shows the main problem is still first-value
comprehension. Stop or remove the heuristic if warnings are less than 80% useful during UAT.
